## Purpose

为维护者和代理提供可发现、可核对的仓库事实入口，使每类变更都能定位代码、公开契约、验证方式和维护责任，并在文档更新或计划迁移后继续保持链接与登记的一致性。

## ADDED Requirements

### Requirement: 仓库入口指向明确的事实来源

仓库 MUST 提供简短入口，区分 core、Studio、文档生成、分发与维护工具，并指向当前事实来源、验证入口和计划位置；不得把已经删除的历史文档作为当前事实来源。

#### Scenario: 定位变更所需上下文

- **WHEN** 维护者从仓库根入口查找 Studio 或 core 的开发说明
- **THEN** 能通过有效本地链接找到对应实现范围、公开契约或文档、检查命令及负责维护角色
- **AND** 生成文件与可编辑源文件有明确区分

#### Scenario: 删除被导航引用的文件

- **WHEN** 入口或维护文档的本地链接目标被删除
- **THEN** 知识入口检查返回非零状态，并指出引用文件和失效目标

### Requirement: 变更类型映射到可解释的验证范围

维护文档 MUST 区分文档、core、Studio 和全量验证范围，说明所需环境、覆盖内容、显式排除项和失败修复入口；纯 core 和文档验证 MUST 不依赖 Node.js 或浏览器。

#### Scenario: 选择核心验证

- **WHEN** 变更作者按文档选择 core 验证
- **THEN** 获得根锁定环境下可执行的命令和覆盖说明，不需要先安装 Studio 或浏览器

#### Scenario: 不能确定变更范围

- **WHEN** 变更涉及多个域或无法可靠分类
- **THEN** 文档指向全量验证，并明确局部成功不代表全量成功

### Requirement: 语言和计划登记保持精确且可审阅

仓库 MUST 保持代码、产品文案、诊断和一般维护文档的英文默认值；用户授权的中文研究与 OpenSpec 文档 MUST 按精确路径及内容摘要登记。检查不得自动更新摘要或扩大豁免目录；失效登记必须报告。

#### Scenario: 清理历史删除留下的例外

- **WHEN** 实施确认旧 OpenSpec 文件已删除且登记不再适用
- **THEN** 仅移除对应失效条目，保留现存中文文档和上游来源登记，语言检查可以重新得到有效基线

#### Scenario: 修改已登记的中文文档

- **WHEN** 文档内容变化但登记摘要未更新
- **THEN** 检查失败并指出不匹配，不自动批准新内容

### Requirement: 计划状态与验证证据明确区分

当前计划 MUST 标明未完成工作及其接受条件；维护文档 MUST 区分计划、已实施事实、历史证据和未验证限制。完成记录必须来自实际执行结果，不得仅因产物生成就宣称实现已完成。

#### Scenario: 提案准备完成

- **WHEN** 提案、设计、规范和任务清单均已生成但任务尚未执行
- **THEN** 记录表示可以开始实施，任务保持未完成，不宣称 CI 或浏览器验收已通过
