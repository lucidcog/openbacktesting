## Purpose

将已确认的包边界和底层依赖约束转换为可执行检查，让新增违规依赖在本地与 CI 中得到明确反馈，同时保留经过审阅的既有接入方式，避免以结构治理之名改变公共行为或来源身份。

## ADDED Requirements

### Requirement: 核心包保持独立于 Studio

架构验证 MUST 拒绝 core 运行时代码和依赖声明引入 Studio、宿主框架或 Studio 资源；Studio 到 core 的单向依赖保持允许。验证报告必须同时区分静态规则与独立安装证明的范围。

#### Scenario: 核心代码新增宿主依赖

- **WHEN** core 代码新增对 Studio 或仅用于宿主的框架导入，或根运行时依赖声明加入这些包
- **THEN** 检查失败并指出文件、规则和依赖目标，不因本机已安装 Studio 而通过

#### Scenario: 独立安装核心包

- **WHEN** 在不含 Studio 和 Node 的环境安装并运行 core 验证样例
- **THEN** 核心计算和打包资源访问成功，报告不将开发环境中的偶然可用性作为独立性证明

### Requirement: 已确认底层模块不得增加高层依赖

依赖检查 MUST 对已审阅的 `data` 和 `broker` 边界阻止向策略、仿真、优化、组合报告、运行编排及其高层兼容入口增加依赖，保留当前合法的类型和公共辅助依赖。规则不得未经证据扩大为全仓理想分层。

#### Scenario: 隐藏在局部或相对导入中的违规边

- **WHEN** 底层模块通过函数内导入、相对导入、别名或可解析重导出引用受禁止的高层能力
- **THEN** 检查识别违规边并失败，诊断包含源文件、位置、目标和修复方向

#### Scenario: 合法类型依赖

- **WHEN** 数据模块使用已确认合法的指标类型或底层辅助能力
- **THEN** 检查通过，不要求为满足理想层级迁移产品代码

### Requirement: 既有内部接入采用精确例外

Studio 到 core 的现存非公开接入 MUST 逐条审阅；允许项必须限定源文件和目标，记录原因、责任角色和移除条件。新增、过宽或已不再匹配的例外必须失败，不得自动把所有当前依赖视为合法基线。

#### Scenario: 新增未审阅内部调用

- **WHEN** Studio 新增未登记的 core 内部依赖
- **THEN** 检查失败并要求选择公开入口或提交明确的例外审阅，既有精确例外不扩展到新文件

#### Scenario: 例外过期

- **WHEN** 例外所对应的导入已移除或文件已删除
- **THEN** 检查报告失效例外，不能让无效登记长期存留

### Requirement: 扫描限制和诊断可审阅

静态检查 MUST 覆盖绝对、相对、类型分支及可静态确定的动态导入，并列明无法解析的动态加载或受控入口。它不得宣称证明所有运行时路径安全；诊断必须提供稳定规则 ID、文件位置、依赖边及修复建议。

#### Scenario: 动态目标无法静态确定

- **WHEN** 遇到不能解析的动态加载
- **THEN** 报告明确覆盖限制或对应受控入口依据，不把该处报告为已经证明无违规

### Requirement: 结构检查不能取代行为契约

统一验证 MUST 保留原有签名、pickle、交易事件、数值与结果 schema 检查；不得为结构检查通过而自动改写这些基线或第三方来源记录。

#### Scenario: 结构合法但行为回归

- **WHEN** 改动符合导入规则但破坏已有结果契约测试
- **THEN** 验证整体失败，结构检查通过不覆盖行为失败
