# User-facing documentation research: backtesting.py

## Conclusion

`backtesting.py` succeeds because its documentation has two deliberately different layers:

1. A short path from data to strategy to results, taught through a Quick Start and focused tutorials.
2. A generated API reference for looking up signatures, parameters, properties, and methods after the user understands the workflow.

The generator is useful for keeping reference pages current, but it is not the information architecture. The user journey is authored first; generated reference pages support it.

## How the upstream documentation is generated and published

- The published package landing page is generated by `pdoc` and explicitly identifies `pdoc 0.11.6` as the generator. It presents the manuals and tutorials before the API reference, then groups the reference by the public submodules `backtesting.backtesting`, `backtesting.lib`, and `backtesting.test`. See the [published landing page](https://kernc.github.io/backtesting.py/doc/backtesting/).
- The repository's [documentation README](https://github.com/kernc/backtesting.py/blob/master/doc/README.md) instructs maintainers to install the documentation extra and run `./build.sh` to build HTML.
- The [build script](https://github.com/kernc/backtesting.py/blob/master/doc/build.sh) runs `pdoc3 --html` over the `backtesting` package, applies a release-only template, checks that each `.ipynb` matches its `.py` counterpart with Jupytext, executes the notebooks with `jupyter-nbconvert`, and scans generated HTML for broken links. The script therefore combines source-derived API output with executable, authored examples.
- The [documentation extra in `setup.py`](https://github.com/kernc/backtesting.py/blob/master/setup.py) names the required tools: `pdoc3`, `jupytext`, `nbconvert`, `ipykernel`, and `jupyter_client`.
- Publication is automated for version tags: the [Deploy docs workflow](https://github.com/kernc/backtesting.py/blob/master/.github/workflows/deploy-docs.yml) installs the documentation/test extras, runs `doc/build.sh`, and invokes the [GitHub Pages deployment script](https://github.com/kernc/backtesting.py/blob/master/.github/deploy-gh-pages.sh). This is build-and-publish automation, not automatic authoring of user guidance.

## What makes the site useful to framework users

### Navigation starts with tasks

The landing page puts the Quick Start and short tutorials before the API. The [Quick Start](https://kernc.github.io/backtesting.py/doc/examples/Quick%20Start%20User%20Guide.html) follows the actual usage sequence:

`data` → `Strategy.init()` and `Strategy.next()` → `Backtest.run()` and `Backtest.plot()` → `Backtest.optimize()` → trade/equity inspection → further examples and the full reference.

Each stage answers a concrete question. It explains the required OHLC data shape, shows a complete strategy, explains when code executes, constructs a backtest, displays returned statistics, and only then introduces optimization and internal result tables. The source is a maintained, readable example notebook/Python pair: [Quick Start Python source](https://github.com/kernc/backtesting.py/blob/master/doc/examples/Quick%20Start%20User%20Guide.py).

### API pages answer “how do I call this?”

The [core API page](https://kernc.github.io/backtesting.py/doc/backtesting/backtesting.html) is module-oriented. It gives each public class a short purpose statement and signature, then documents methods and properties in separate groups. For example, `Backtest` immediately exposes constructor parameters and explains data requirements, execution settings, and the next calls (`run`, `optimize`, and `plot`). `Strategy` explains the lifecycle (`init` then `next`), data access, indicator declaration, order placement, and position/trade access. `Order`, `Position`, and `Trade` are presented as the objects a strategy user encounters while trading.

The page uses links between related objects instead of repeating the same explanation. A method points to the class or property that supplies its parameter semantics, and the page's sidebar provides class/method anchors for direct lookup. The signatures are visible, but behavioral rules and examples carry the user-facing meaning.

The [utility module page](https://kernc.github.io/backtesting.py/doc/backtesting/lib.html) applies the same pattern to helpers and composable strategies. It groups functions and classes, states when each helper is appropriate, and includes small examples for functions whose calling convention is not obvious, such as `crossover`, `compute_stats`, and `resample_apply`. The page also states the module's scope, which prevents users from treating it as a replacement for specialist indicator libraries.

### Examples are part of the API explanation

The Quick Start does not merely list API names. It shows a complete strategy, explains the two-phase lifecycle, demonstrates `self.I`, shows order calls, runs the backtest, plots it, optimizes class parameters, and inspects `_equity_curve` and `_trades`. The API pages then link back to those examples. This makes examples the shortest route to understanding a class while keeping the reference available for exact parameter lookup.

## Applicable principles for OpenBacktesting

The current repository already has a useful skeleton: the [manual index](../core/index.md) routes to a Quick Start, guides, runnable examples, and module reference pages. The [development guide](../core/development.md) also records that handwritten guides are preserved while `core_docs.py` generates references. The gap to close is the user-facing contract on each page, rather than adding more raw API inventory.

1. **Define the information architecture by user jobs.** Make the first route a single runnable backtest, then branch to data, strategy lifecycle, indicators, execution, orders/positions/trades, results/plotting, optimization, and advanced/runtime integrations. Keep this route visible from the manual index.
2. **Give every public module a user-facing entry page.** Cover the core areas users must combine: data/context, strategy, indicators, backtest/engine, broker configuration, order, position, trade, results/portfolio, optimization, plotting, and runtime. Each page should begin with purpose, import path, and a minimal runnable example before listing the complete surface.
3. **Use a consistent page contract for each public class.** Show the import path; one-sentence purpose; constructor or factory signature; parameter meanings, accepted shapes/types, defaults, and constraints; lifecycle or state transitions; the most common methods and properties; one complete usage example; and links to related classes and the relevant guide. Group methods by user task or lifecycle rather than emitting one undifferentiated symbol list.
4. **Make signatures precise but keep explanations selective.** Generated signatures are valuable for lookup. Generated output should omit private/internal objects and compatibility clutter from the primary user route; internal/source provenance can remain available in a secondary developer section when needed.
5. **Use examples as executable documentation.** Keep one short example per major workflow and link every example to the API anchors it uses. Build validation should execute examples or notebooks, check generated pages are current, and check links. A syntax check alone cannot prove that a user can follow the documented workflow.
6. **Curate the indicator surface.** Organize indicators by the user's lookup task (category/name), show a uniform call pattern, and include a tiny example plus output shape/meaning. Keep implementation details and private helpers out of the main catalog. The catalog can be generated, but names, descriptions, use cases, and example relationships require reviewed source-of-truth metadata.
7. **Keep the generated/manual boundary explicit.** Treat source docstrings, signatures, and reviewed catalogs as inputs to generated references. Treat the manual, guides, and examples as authored product documentation. Regeneration must never replace the latter, and a stale generated page should fail validation rather than silently drift.

## Non-goals

- Do not turn the user site into a dump of every module, private helper, compatibility alias, or source file. Contributors can inspect the repository; users need stable public entry points and working recipes.
- Do not rely on an API generator to invent the usage journey or replace explanations of lifecycle, state, data shape, execution timing, result shape, and common failure modes.
- Do not copy the upstream framework's names or semantics where OpenBacktesting differs. Reuse the separation of concerns and presentation pattern, then document this repository's actual contracts.
- Do not make the first release depend on a documentation framework solely for visual polish. A static Markdown manual plus generated reference pages is sufficient if navigation, examples, and validation are strong; a website build is a later delivery choice.
- Do not treat every indicator or low-level broker type as equally important in the top-level navigation. Complete public coverage can exist behind categorized reference pages while the main route remains task-focused.

## Evidence limits

The upstream sources establish the structure, pdoc build, executable-example checks, and tag-based deployment described above. They do not prove that every design choice is optimal for OpenBacktesting, nor do they provide a direct measure of user satisfaction. The OpenBacktesting recommendations above are an application of those observable mechanisms to the current repository and should be validated against actual user tasks and runnable examples.
